Version Compaction

Every version accumulates finished and pending work. Compaction lets you close that chapter: it freezes the tasks that are already Done into an immutable summary, removes them from the version and leaves the pending work where it is.

The version keeps its identity, but its completed history now lives in the summary instead of the task list. This keeps long-lived versions lightweight and gives you a stable record of what a release actually contained.

What compaction does

Section titled “What compaction does”

Compacting a version:

  • Takes every task with status Done, along with its notes and dependencies.
  • Stores them in a snapshot inside a summary.
  • Deletes those Done tasks from the version.
  • Leaves Todo tasks untouched in the version.

The summary is written in one transaction with the deletion, so a failure never removes tasks without saving the snapshot.

Caution

Compaction is destructive for the task list. Done tasks are deleted from the version once frozen, and deleting a summary does not bring them back.

The snapshot

Section titled “The snapshot”

The frozen snapshot is a point-in-time JSON document that contains:

  • The version it belongs to.
  • The Done tasks, including their completed_at timestamp.
  • The notes attached to those tasks.
  • The dependency links recorded for them.
  • The previous summary, when the version is being recompacted.

Keeping completed_at, notes and dependencies means the summary still answers what was finished, when and how it related to the rest of the work after the tasks are gone.

Compact a version

Section titled “Compact a version”

Compaction is driven by the MCP server, so an MCP client or AI assistant can run it while you review the result. The full cycle is:

  1. preview_compact_version — inspect what would be frozen.
  2. compact_version — write the summary and delete the Done tasks.
  3. list_version_summaries / read_version_summary — review the result.
  4. export_version_summary — write a Markdown copy.
  5. delete_version_summary — discard the summary (optional).

All tools use the version_id and require the MCP server to be connected as described in the MCP server guide.

Preview

preview_compact_version returns the exact JSON snapshot that compact_version would store, without changing anything:

Run it first to confirm which tasks are Done, which notes they carry and which dependencies will be frozen.

Run the compaction

Section titled “Run the compaction”

compact_version takes the version id and a required summary — a prose description of the release that you want to keep alongside the snapshot:

mark_released is optional and defaults to true. The resulting version status depends on what remains in it:

Remaining tasks mark_released Version status
Any Todo task ignored Becomes Open (also from Backlog)
None true (default) Becomes Released
None false Unchanged

In other words, a partial compaction never releases a version that still has pending work, even if every existing task was Done.

The operation fails when:

  • Any task in the version is In Progress — finish it or move it back to Todo first.
  • There is nothing to freeze: no Done tasks and no previous summary.

Recompact a version

Section titled “Recompact a version”

A version holds at most one summary. Running compact_version again replaces the previous summary with a new one that includes the newly finished tasks.

The preview of a recompaction exposes the previous summary as previous_summary, including its own snapshot. Use it to write the new prose: the new summary should preserve the relevant knowledge from the previous one while adding what changed, because the old prose is replaced.

Review a summary

Section titled “Review a summary”

In the TUI

Section titled “In the TUI”

Open the version in the TUI and use these keys:

Key Action
s Open the latest summary
e Export the latest summary to Markdown

Both keys only act when the version already has a summary.

The summary screen shows the prose with a scrollable view (j / k to move, Esc to go back) and a Distribution block with counts per status (done, todo, in_progress) and per priority (high, medium, low).

With MCP

Section titled “With MCP”
Tool What it returns
list_version_summaries The summaries of a version, newest first
read_version_summary The summary prose plus its frozen snapshot JSON

Both read_version_summary and delete_version_summary take a version_id and a summary_id. If the summary does not belong to that version, the tool reports not found.

The same data is available as read-only resources: pmp://versions/{id}/summaries lists the summaries of a version and pmp://summaries/{id} reads a single one.

Export a summary

Section titled “Export a summary”

export_version_summary writes a self-contained Markdown file and returns its path:

The document includes the prose summary, the generation date, Mermaid charts and a task table with notes:

  • A pie chart of tasks by status.
  • A pie chart of tasks by priority.
  • A dependency flowchart, included only when the version has 20 tasks or fewer. For larger versions the export adds a note explaining that the flowchart was omitted.
  • A table of tasks with creation and completion dates.
  • The notes of each task.

The export always lands in the exports folder inside PMP’s data directory; the tool does not accept a destination path. In the TUI, pressing e runs the same export and shows Exported to <path> with the resulting file.

See Configuration for the data directory location on each operating system.

Remove a summary

Section titled “Remove a summary”

delete_version_summary deletes the summary artifact, for example when it was created by mistake:

It does not restore the Done tasks deleted during compaction. Remove a summary only when you are sure you no longer need the frozen record.

Example workflow

Section titled “Example workflow”

A typical release close-out looks like this:

  1. Finish every task you want in the release and mark it Done.
  2. Run preview_compact_version and check the snapshot.
  3. Run compact_version with a summary of the release and let it mark the version Released.
  4. Open the version in the TUI, press s to review it and e to export the Markdown.
  5. Share the exported file or keep it with the release notes.
